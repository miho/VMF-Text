# AGENTS.md

## Instructions for coding agents (Cursor Cloud, Claude Code, and others)

### What this project is
VMF-Text is a Java/Gradle framework that turns a labeled ANTLR4 grammar into a
clean (un)parsing/transformation API (built on the separate VMF modeling
framework). It is a library/CLI-style framework, not a running server or GUI.

Three Gradle subprojects build in a strict order because each publishes an
artifact (version in `config/common.properties`) to the local Maven repo that
the next one consumes:
1. `core` → `publishToMavenLocal` (produces `eu.mihosoft.vmf:vmf-text`)
2. `gradle-plugin` → `publishToMavenLocal` (consumes `vmf-text`, produces `vmf-text-gradle-plugin`)
3. `test-suite` → `test` (consumes `vmf-text-gradle-plugin` to generate + test grammars)

Standard build/test commands are already documented in `README.md`,
`build-all.sh`, and `build-and-test-all.sh`. `build-and-test-all.sh` runs the
full chain above. Always use the Gradle wrapper (`./gradlew`, Gradle 9.8.2); CI
uses `--no-daemon`. If you hit `Permission denied`, invoke it as `sh ./gradlew`.

### Upstream dependency: VMF
`core` depends on the sibling VMF project (`eu.mihosoft.vmf:vmf`,
`:vmf-runtime`, and the `eu.mihosoft.vmf` Gradle plugin =
`:vmf-gradle-plugin`). Releases are on Maven Central (`0.2.11` is the latest);
`main` currently depends on `0.2.12-SNAPSHOT` (generated list `equals` fix
miho/VMF#87, Gradle 10 fixes, plugin marker on Central, a VMF Gradle plugin
that resolves its classpath lazily miho/VMF#89, and since the build of
2026-10-21, build 4, setters that compare model values by identity,
containment opposites declared in a base type, release from the previous
container by identity and for subtypes, and no container property id for a
containment without opposite, miho/VMF#91 — the containment model of the
generated code needs that build), which the builds
resolve from the Central snapshot repository
(`https://central.sonatype.com/repository/maven-snapshots/`, declared in
`core/settings.gradle`, `core/build.gradle`, `gradle-plugin/build.gradle`,
`test-suite/build.gradle`, the ArrayLang example, and added to consumer
projects by the plugin, scoped to `eu.mihosoft.vmf` snapshots). A plain
checkout builds without extra steps. Gradle trusts a cached `-SNAPSHOT` for
24 h, so after a new VMF snapshot build run the `core` build once with
`--refresh-dependencies` (CI does so on every run). When VMF is released next,
pin the release in those places (and `README.md`, `VMFTextPlugin.groovy`),
drop the repository and the CI flag.
Building VMF from source is only needed for unpublished VMF work:

```
git clone --depth 1 https://github.com/miho/VMF.git ~/deps/VMF
cd ~/deps/VMF && sh ./gradlew clean publishToMavenLocal --no-daemon
```
(VMF pins JDK 17 toolchains for that source build.)

### JDK toolchains
Gradle 9 itself runs on JDK 17+, but the projects pin a Java toolchain that
must be installed locally (no toolchain auto-download is configured):
- VMF-Text `core`, `gradle-plugin`, `test-suite` → JDK 21

If a build fails with "Cannot find a Java installation ... matching
{languageVersion=NN}", install that JDK (e.g. on Debian/Ubuntu
`sudo apt-get install -y openjdk-<NN>-jdk`) or make it visible to Gradle via
`org.gradle.java.installations.fromEnv` (this is how CI does it).

### CI
`.github/workflows/ci.yml` runs on every push and pull request: it builds the
full chain above against the released VMF from Maven Central and runs the
complete test suite. Keep it green — there is no other automated gate.

### Non-obvious gotchas
- No cross-project hot reload: subprojects talk to each other only through
  `~/.m2` snapshots. After editing `core`, re-run `core` `publishToMavenLocal`
  (and usually `gradle-plugin` too) before `test-suite` will see the change.
- Lint: there is no lint or license-header task (the former
  `com.github.hierynomus.license` plugin was removed in 0.2.2 — it was
  unmaintained, ran with `ignoreFailures = true`, and breaks under Gradle 10).
  Copy the header from `core/config/HEADER` into new source files by hand.
- Gradle 10 readiness: the three builds must stay free of Gradle deprecation
  warnings (`sh ./gradlew help --warning-mode all` prints none). Use
  `prop = value` assignment, `layout.buildDirectory` instead of `buildDir`, and
  resolve paths at configuration time instead of touching `project` inside
  `doLast`.
- Windows: the test-suite has deeply nested paths. A checkout or worktree under
  a long base path fails with `Filename too long` unless
  `git config core.longpaths true` (or `git -c core.longpaths=true ...`).
- Tests live in `test-suite`; HTML report at
  `test-suite/build/reports/tests/test/index.html`. Grammars under
  `test-suite/src/main/vmf-text/**` are code-generated by the plugin at build
  time (task `vmfTextGenTestCode`).
- Native toolchain: `miniclang`'s `parseUnparseRunCodeTest` compiles and runs the
  *unparsed* C at runtime via the `vtcc` (Tiny C Compiler) wrapper. In sandboxes
  where TCC cannot link libc it fails with `tcc: error: library 'c' not found`
  (empty program output) even though parse/unparse is correct — an environment
  limitation, not a codegen defect. Tracked in
  [#23](https://github.com/miho/VMF-Text/issues/23); CI with a full toolchain is
  unaffected.
